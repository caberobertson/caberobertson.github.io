Problem

Why it exists

Every year, thousands of car crash victims suffer preventable deaths because emergency response is delayed, most critically when the driver is incapacitated and cannot call for help. CrashGuard closes that gap: it identifies a collision on its own from a sudden change in acceleration, then contacts help without requiring any action from the occupant.

The board becomes the "brain" of an in-vehicle guardian. When it detects an impact, a live phone dashboard flashes a ten-second countdown while the onboard buzzer sounds. A conscious occupant taps one big red CANCEL button and the system re-arms. If nobody cancels, CrashGuard assumes the occupant is incapacitated and escalates to an AI voice call that reports who they are, where they are, and what a dispatcher needs to know.

01

The chain of events

From impact to a dispatcher answering the phone, with a human override at the only point where one belongs.

  1. Detect. The accelerometer is sampled at 100 Hz; a normalized magnitude above the calibrated threshold declares a collision.
  2. Warn. The phone dashboard flashes !! CRASH DETECTED !! with a ten-second countdown and vibrates; the buzzer on the car beeps faster in the final three seconds.
  3. Offer the override. One tap on CANCEL - I'M OK dismisses the alert and re-arms the system, exactly how a conscious driver waves off a pothole.
  4. Escalate. If the countdown expires, the board pushes a Bluetooth alert to the host, which fires the call pipeline.
  5. Locate. A single batch of map lookups resolves the address, city, nearest cross streets, and closest hospitals from the live GPS fix.
  6. Call. Twilio places an outbound call that speaks the occupant's briefing, then a Claude agent answers the dispatcher's follow-up questions using only verified data.
  7. Document. After a few exchanges the system offers to send a full written incident report by SMS or email.
02

Impact detection

A self-calibrating baseline makes the threshold independent of library scale factors and mounting orientation.

Method

The MPU6050 accelerometer/gyroscope module (I2C address 0x69) is sampled at 100 Hz with the full-scale range set to ±16 g so crash spikes are never clipped. At boot the firmware averages one hundred samples while the vehicle is still, learning what 1 g actually reads as on this board and this mounting. Every later reading is normalized against that measured baseline:

G = |a| / |a|baseline   where  |a| = √(ax² + ay² + az²)

A collision is declared when G exceeds the calibrated detection threshold, set at 50 g for impact events. The threshold is tuned from labelled normal and crash runs recorded with the included calibration tool, and paired with GPS filtering to eliminate false positives in field testing.

Engineering lesson. A consumer accelerometer cannot give you trustworthy velocity by integration, drift swamps the signal. But a sudden high-magnitude change in acceleration is a robust, low-cost crash signature, and normalizing against a measured baseline is what makes the threshold portable between boards.
03

The phone dashboard

The demo vehicle is moving, so every result belongs on a phone, not on a screen bolted to the car.

The board streams its status (current G, session peak, state, and countdown seconds) off-board five times per second. The call server renders it as a mobile web dashboard on the local network, so any phone can open it with no app install.

The instant an impact is confirmed the dashboard goes full-screen with the countdown and a large red CANCEL - I'M OK button, and the phone vibrates. One tap cancels and re-arms. The onboard pushbutton stays wired as a backup, and after an alert the dashboard offers a RE-ARM control.

  • Live telemetry: impact G and session peak, updated 5×/second
  • Ten-second cancel window: full-screen countdown with haptic feedback
  • Backup input: onboard hardware button mirrors the CANCEL action
  • Re-arm: return the system to monitoring after a cancelled or completed alert
04

Systems behind the call

Four subsystems turn a detected impact into a conversation a dispatcher can actually use.

Link

Wireless link

BLE GATT ESP32 Wi-Fi fallback

The ESP32 runs a BLE GATT server with three characteristics: crash alerts out, live status out, and phone commands (CANCEL / REARM) in. A Python bridge relays alerts upward and button presses back down. For noisy conference radio environments, a compile-time flag switches the board onto a phone hotspot and talks to the server over HTTP instead; each status POST returns any pending command, so no bridge is needed at all.

Context

Map intelligence

OpenStreetMap Nominatim Overpass

A dispatcher asks things no profile can hold: what's the nearest cross street? what city is this? where's the closest ER? At the moment of the crash CrashGuard runs one batch of key-less OpenStreetMap lookups against the live GPS fix (address, city and county, nearest named roads, and closest hospitals with distance and compass direction) and injects the bundle into the AI's context. Fetching once keeps answers fast and grounded in real map data instead of guesswork.

Voice

The AI dispatcher agent

Twilio Voice Claude API Flask

The Flask call server receives the crash event and uses Twilio to place the outbound call. It opens with a spoken briefing (name, GPS coordinates and nearest address, peak impact force, blood type, medical conditions, primary emergency contact), then listens. The dispatcher's speech is transcribed and handed to a Claude agent whose system prompt contains only the occupant profile and live crash data, instructed to answer in one to three short sentences, read numbers digit by digit, and say "I don't have that information" rather than ever guess.

Record

Incident documentation

SMS SMTP Intent parsing

After a few exchanges CrashGuard offers to document everything, then asks whether to send it by text or email and delivers a formatted report: timestamp, peak impact, coordinates, address, cross streets, nearest hospitals, occupant identity, blood type, conditions, allergies, medications, emergency contacts, and vehicle details. The whole exchange is handled by local intent parsing rather than the language model, so it adds no per-call AI cost and responds instantly.

Specifications & stack

Stack

What it is built from

  • MYOSA Mini Kit: ESP32 motherboard, MPU6050 accelerometer/gyro, buzzer and pushbutton on the I2C chain
  • Arduino (C++): firmware, official MYOSA sensor libraries, ESP32 BLE stack
  • Python 3 + HTML/JS: Flask call server, live mobile dashboard, bleak BLE bridge, pyserial calibration tooling
  • OpenStreetMap: Nominatim and Overpass for reverse geocoding, cross streets, and nearby hospitals (free, no API key)
  • Twilio Programmable Voice: outbound calling, speech recognition, neural text-to-speech
  • Claude API: grounded conversational dispatcher agent

06

Status & what's next

Roadmap

The full chain (detection, cancel window, BLE alert, AI call, map lookups, and incident reporting) runs end to end on the prototype above. Work continues on hardening the demo and extending the system:

  • Rollover detection using the gyroscope alongside the acceleration threshold
  • Phone app to replace the laptop bridge, which would bring real phone GPS into the alert
  • LTE alert path for genuinely standalone operation with no host nearby
  • Additional language support for the dispatcher agent
